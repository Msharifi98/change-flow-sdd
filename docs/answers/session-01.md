سؤال ۱ — Constitution و حاکمیت معماری
تیم شما تصمیم گرفته تمام Business Logic در لایهٔ Domain یا Application قرار بگیرد و API فقط مسئول دریافت درخواست و ارائهٔ پاسخ باشد. Coding Agent قابلیتی را پیاده‌سازی کرده و همهٔ تست‌ها موفق شده‌اند؛ اما بخشی از Business Logic مستقیماً داخل Controller یا Endpoint نوشته شده است.

تفاوت موفقیت تست‌ها با رعایت اصول معماری چیست؟
پاس شدن تست‌ها لزوماً به معنای درست بودن معماری نیست. تست‌ها رفتار مورد انتظار یک واحد را بررسی می‌کنند، اما اصول معماری به نحوهٔ پیاده‌سازی، جداسازی مسئولیت‌ها، نگه‌داری‌پذیری و مقیاس‌پذیری پروژه مربوط می‌شوند. ممکن است متدی در Controller هم اعتبارسنجی، هم منطق کسب‌وکار و هم تغییر وضعیت را انجام دهد و تست‌هایش پاس شوند، ولی اصل جداسازی مسئولیت‌ها نقض شده باشد.

قاعدهٔ جداسازی مسئولیت‌ها باید در Constitution، Plan یا Tasks ثبت شود؟ چرا؟
در Constitution، چون این قاعده یک اصل معماری دائمی و بنیادین پروژه است.

Constitution: قوانین اصلی و همیشگی معماری

Plan: نحوهٔ اعمال آن قانون در طراحی هر فیچر

Tasks: اقدامات اجرایی برای رعایت قانون

سؤال ۲ — Specify و Clarify
مالک محصول می‌گوید: «کارمندان بتوانند درخواست ثبت کنند و مدیرها بعد از بررسی، درخواست‌ها را تأیید کنند.» Coding Agent فرض می‌کند هر مدیری می‌تواند درخواست خودش را نیز تأیید کند.

آیا Agent مجاز است این تصمیم را بدون تأیید مالک محصول نهایی کند؟
خیر. این یک تصمیم محصولی است؛ Agent می‌تواند پیشنهاد بدهد، اما تصمیم نهایی و مسئولیت آن با مالک محصول است.

تفاوت Assumption با تصمیم تأییدشدهٔ مالک محصول چیست؟
Assumption فرضی است که به‌دلیل کمبود اطلاعات و برای جلوگیری از توقف کار گرفته می‌شود، در حالی که تصمیم تأییدشده حاصل بررسی جنبه‌های مختلف توسط مالک محصول است و مسئولیت آن نیز بر عهدهٔ اوست.

حداقل دو ابهام مهم دیگر در این درخواست پیدا کنید.

هر مدیر چه درخواست‌هایی را بررسی می‌کند؟ درخواست‌های کل سازمان یا فقط واحد و تیم خودش؟

آیا امکان بازگرداندن درخواست برای اصلاح وجود دارد؟ اگر بله، درخواست‌دهنده چه اطلاعاتی را می‌تواند ویرایش کند؟

کدام ابهام‌ها باید در Specify برجسته شوند و Clarify چه نقشی در رفع آن‌ها دارد؟
در Specify، نیازمندی‌ها، محدودیت‌ها و رفتارهای مورد انتظار مشخص می‌شوند و هر جا اطلاعات برای تعریف رفتار کافی نباشد، ابهام‌ها شناسایی و مستند می‌شوند. در Clarify این ابهام‌ها با مالک محصول بررسی، پاسخ دریافت و تصمیم نهایی ثبت می‌شود.

سؤال ۳ — Requirement در برابر Design Decision
در Specification آمده است: «هیچ درخواست تأییدشده‌ای نباید با محتوای تغییرکرده، بدون بررسی و تأیید معتبرِ آن محتوا، اجرا شود.» توسعه‌دهنده پیشنهاد می‌کند یک فیلد عددی به نام ContentRevision اضافه کنیم.

کدام بخش Requirement است و کدام بخش Design Decision؟
جملهٔ «هیچ درخواست تأییدشده‌ای نباید با محتوای تغییرکرده... اجرا شود» یک Requirement است، چون رفتار و محدودیت را بیان می‌کند بدون تعیین نحوهٔ پیاده‌سازی. پیشنهاد افزودن ContentRevision یک Design Decision است، چون روش فنی پیاده‌سازی آن نیازمندی را پیشنهاد می‌دهد.

چرا بهتر است مکانیزم فنی در Plan/Research بررسی شود؟
برای یک نیازمندی معمولاً چند راهکار فنی وجود دارد و باید بر اساس محدودیت‌ها، پیچیدگی و هزینه، تصمیم نهایی از قبل گرفته شود.

حداقل دو راهکار جایگزین برای تشخیص محتوای تأییدشده پیشنهاد کنید و Trade-off آن‌ها را توضیح دهید.

۱. Version Numbering — با هر تغییر، نسخهٔ پیش‌نویس از اطلاعات تأییدشده نگه داشته می‌شود و پس از تأیید جایگزین نسخهٔ اصلی می‌شود. در Spring Boot می‌توان از @Version در JPA استفاده کرد.

مزایا: پیاده‌سازی ساده، مقایسهٔ سریع

معایب: افزایش حجم ذخیره‌سازی به مرور زمان

۲. Content Hash — از محتوای درخواست هش (مثل SHA-256) تولید و هنگام تأیید ذخیره می‌شود؛ هنگام اجرا هش محتوای فعلی محاسبه و با مقدار ذخیره‌شده مقایسه می‌شود.

مزایا: تشخیص تغییر حتی خارج از مکانیزم Version، عدم وابستگی به شمارهٔ نسخه، اطمینان از یکسانی محتوای تأییدشده و اجراشده

معایب: نیاز به تعریف دقیق فیلدهای مؤثر در هش، حساسیت به نحوهٔ Serialization، عدم نگهداری تاریخچهٔ تغییرات

سؤال ۴ — Tasks و Analyze
برای یک Feature، ۳۰ Task تولید شده و هر Requirement حداقل به یک Task مرتبط است. با این حال، یک Task به دیتابیس آماده نیاز دارد در حالی که Migration دیتابیس در Task بعدی تعریف شده است. همچنین دو Task دارای نشانگر [P] باید فایل مشترکی را تغییر دهند.

چه مشکلاتی در Dependency و Parallelism وجود دارد؟
ترتیب وابستگی‌ها اشتباه است؛ Migration دیتابیس باید قبل از Task وابسته به آن انجام شود. همچنین نشانگر [P] به‌درستی اعمال نشده، چون دو Task موازی نمی‌توانند فایل مشترک را بدون ریسک Conflict تغییر دهند. راه‌حل: ترتیبی کردن این دو Task یا تجمیع تغییرات فایل مشترک در یک Task.

انتظار دارید Analyze چه Findingهایی گزارش کند؟

وابستگی‌های تسک: آماده بودن پیش‌نیازهای هر Task قبل از اجرا

Conflictهای اجرای موازی: شناسایی Taskهایی که اجرای موازی‌شان Conflict ایجاد می‌کند

ترتیب اجرای تسک‌ها: شناسایی و گزارش ترتیب نادرست

ریسک‌های پیاده‌سازی: ریسک‌های ناشی از اجرای ناقص یا Conflict

بررسی ارتباط Requirements، Tasks و Design Decisions برای اطمینان از پوشش کامل

آیا پوشش ۱۰۰٪ Requirementها توسط Tasks، آمادگی قطعی برای Implement را ثابت می‌کند؟ چرا؟
خیر. فقط نشان می‌دهد برای هر نیازمندی حداقل یک اقدام اجرایی وجود دارد؛ اما صحت طراحی را تضمین نمی‌کند. ممکن است وابستگی‌ها اشتباه باشند یا Tasks با Design Decisions سازگار نباشند.

سؤال ۵ — Implement، Validation و Converge
Coding Agent گزارش داده است: «تمام Taskها تکمیل شده‌اند؛ پروژه Build شده و ۱۲۰ Test همگی Passed هستند.» اما در Code Review متوجه می‌شوید یک قاعدهٔ امنیتی رعایت نشده و یک معیار پذیرش انسانی هنوز ارزیابی نشده است.

آیا Feature قابل اعلام به‌عنوان «کامل و پذیرفته‌شده» است؟
خیر. این گزارش فقط نشان می‌دهد پروژه بدون خطای ساختاری Build می‌شود؛ اما ممکن است برخی الزامات (امنیت، معیارهای پذیرش) به‌درستی پیاده‌سازی یا ارزیابی نشده باشند.

تفاوت Build، Test، Validation و Acceptance چیست؟

Build: قابلیت تبدیل کد و وابستگی‌ها به فایل اجرایی

Test: بررسی رفتار بخش‌های مختلف سیستم در برابر سناریوهای تعریف‌شده

Validation: مطابقت پیاده‌سازی با محدودیت‌ها و معیارهای مورد انتظار (تست خودکار، بررسی امنیتی و...)

Acceptance: تأیید نهایی مسئول مربوطه مبنی بر برطرف شدن نیازمندی توسط فیچر

Converge در این وضعیت چه نقشی دارد و چه تفاوتی با Analyze دارد؟
هر دو کیفیت و سازگاری کار را بررسی می‌کنند، اما هدفشان متفاوت است:

Analyze: قبل از پیاده‌سازی؛ بررسی منطقی و کامل بودن طراحی و برنامهٔ اجرایی

Converge: بعد از پیاده‌سازی و Validation؛ بررسی فاصلهٔ بین وضعیت واقعی کد و مستندات

اگر Converge شکاف جدیدی پیدا کند، مسیر اصلاح چیست؟
شکاف باید بررسی و به یک Task مشخص تبدیل شود تا در چرخهٔ بعدی توسعه رفع گردد.
